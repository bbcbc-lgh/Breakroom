# 赛博小镇需求规格

状态：Approved v1.0，已于 2026-08-02 确认

阶段门：本文件确认前不进入系统设计；设计确认前不制定开发计划；开发计划确认前不编写业务代码。

## 1. 产品目标

构建一个 Windows 桌面端的 2D 像素风 AI 小镇可发布原型。玩家在办公室场景中自由移动，与三名拥有不同身份、性格、记忆和关系状态的 NPC 进行自然语言对话，并能观察关系随互动发生变化。

首版以可发布、可运行、可验证为优先，同时保留 CyberTown（第十五章）作为游戏架构原型的演进价值。它不是 Helix 的后续版本，也不依赖 Helix 源码；可以借鉴已有 Agent、上下文和记忆设计，但必须形成 CyberTown 自己的领域模型、接口和类名。

## 2. 已确认决策

- 引擎：Godot 4.7.1，目标分辨率 1280 x 720。
- 后端：Python + FastAPI。
- 玩家模式：首版单人，但数据从一开始按 `player_id + npc_id` 隔离。
- AI 接入：先用 mock 模式跑通完整链路，再接入真实 LLM。
- 持久化：首版仅使用 SQLite；Qdrant 和 Neo4j 延后。
- 语言：简体中文。
- 美术：首版使用原创占位像素资源，功能稳定后可替换。
- NPC：首版使用张旭、樊玥燚、胡佳烙三名 NPC。
- 版本管理：`CyberTown` 作为独立 Git 仓库，不将父目录 `HelloAgents` Git 化。

## 3. 目标用户与核心体验

目标用户是希望体验 AI NPC、验证游戏与智能体结合方式的 Windows 桌面玩家和开发者。

核心体验闭环：

1. 玩家启动游戏，进入一个可探索的像素办公室。
2. 玩家使用 WASD 移动，并受到墙体、家具和角色碰撞约束。
3. 玩家靠近 NPC 后看到交互提示，按 E 打开对话界面。
4. 玩家输入自然语言，立即看到发送和等待状态；世界和界面不能因后端等待而失去响应。
5. NPC 根据角色设定、当前关系、近期对话和已保存记忆回复。
6. 对话、记忆事件和关系变化写入 SQLite；重新启动后仍可恢复。
7. 模型或后端不可用时，游戏给出明确的降级反馈，玩家仍能移动、关闭对话并继续体验。

## 4. 首版 NPC 设定

以下设定是首版默认内容，不是写死在业务代码中的限制。

| NPC | 职业 | 核心性格 | 对话侧重点 |
| --- | --- | --- | --- |
| 张旭 | Python / AI 工程师 | 严谨、直接、重视证据和代码质量 | 技术实现、调试、工程实践 |
| 樊玥燚 | 产品策划 | 外向、善于倾听、习惯追问目标和用户价值 | 产品需求、体验、项目规划 |
| 胡佳烙 | 视觉与交互设计师 | 温和、敏锐、富有创意、表达具体 | 视觉设计、交互细节、创意灵感 |

NPC 配置至少包含：稳定 ID、显示名称、职业、性格、说话风格、背景简介、话题偏好、行为边界、关系阶段表达规则、场景出生位置、外观标识和是否启用巡逻。

必须支持通过数据配置新增、删除或修改 NPC，而不修改对话、记忆、关系等业务代码。配置错误必须给出可定位的校验信息，不能静默使用错误数据。

首版采用本地配置文件修改 NPC，启动时完成校验，重启后生效；不开发游戏内 NPC 管理后台，也不要求运行时热更新。

## 5. 功能需求

### 5.1 游戏场景与操作

- `FR-GAME-01`：提供一个完整的俯视角像素办公室场景，包含明确的可行走区、墙体、家具、三名 NPC 和玩家出生点。
- `FR-GAME-02`：玩家可使用 WASD 移动，角色移动具有方向反馈，不能穿过墙体、家具或 NPC。
- `FR-GAME-03`：NPC 可在受限区域内进行低频巡逻；不得走出场景、穿过障碍或在对话时继续移动。
- `FR-GAME-04`：玩家进入 NPC 交互范围时显示“按 E 交互”，离开后提示消失；同时靠近多个 NPC 时只能选定一个明确目标。
- `FR-GAME-05`：对话期间禁用玩家移动，关闭对话后恢复；游戏主循环不得等待 LLM 或 HTTP 请求。
- `FR-GAME-06`：NPC 可显示短时背景气泡。首版内容允许由本地模板产生，不要求使用 LLM 批量生成。

### 5.2 对话体验

- `FR-DIALOGUE-01`：对话界面显示 NPC 姓名、职业、关系等级、对话历史、输入框、发送按钮、等待状态和关闭按钮。
- `FR-DIALOGUE-02`：玩家可发送非空中文文本；系统限制输入长度并阻止等待期间重复提交。
- `FR-DIALOGUE-03`：mock 模式必须提供符合 NPC 人设的确定性回复，使没有 API 密钥时仍能完成全部核心流程。
- `FR-DIALOGUE-04`：真实模型模式下，回复必须结合 NPC 配置、关系阶段、最近对话和检索到的长期记忆。
- `FR-DIALOGUE-05`：不同 NPC 的表达应可区分；NPC 不得声称能执行游戏中不存在的动作或访问终端、文件、任意网络和数据库写入工具。
- `FR-DIALOGUE-06`：请求超时、服务错误或响应无效时显示稳定的 NPC 降级回复和可重试状态，不泄露内部异常或密钥。

### 5.3 记忆系统

- `FR-MEMORY-01`：短期上下文按 `player_id + npc_id` 保存最近对话，保证代词和连续追问可以理解。
- `FR-MEMORY-02`：长期记忆首版存入 SQLite，以结构化记忆事件为主，并提供不依赖向量数据库的检索能力。
- `FR-MEMORY-03`：NPC 能在后续会话中回忆玩家明确提供的姓名、偏好或已讨论事件；服务重启后记忆仍存在。
- `FR-MEMORY-04`：记忆具有来源对话、NPC、玩家、时间和重要性信息；不同 NPC、不同玩家的记忆不得串线。
- `FR-MEMORY-05`：上下文有数量或长度预算，无关历史不能无限进入模型请求。

### 5.4 关系系统

- `FR-RELATION-01`：每个玩家与每个 NPC 拥有独立的 0 至 100 关系分数和陌生、熟悉、友好、亲密、挚友五个等级。
- `FR-RELATION-02`：关系变化由确定性规则决定。模型可以输出受限的互动标签，但不能直接写入分数。
- `FR-RELATION-03`：关系规则应支持正向、中性和负向变化，并具备单次上限、重复内容抑制或冷却机制，避免刷分。
- `FR-RELATION-04`：每次变化保存旧值、新值、变化量、规则 ID、原因和来源事件，且可在日志中追踪。
- `FR-RELATION-05`：关系等级会影响 NPC 的措辞、分享程度和主动关心程度；界面至少展示等级，分数是否直接展示由设计阶段确定。

### 5.5 NPC 配置与状态

- `FR-NPC-01`：Godot 和后端使用同一个稳定 `npc_id` 识别 NPC，显示名称可以修改且不破坏已有关系和记忆。
- `FR-NPC-02`：场景从后端或共享数据源加载 NPC 可展示配置，不在多个脚本中重复写死名字、职位和性格。
- `FR-NPC-03`：后端提供 NPC 列表与可展示状态，包括背景气泡、是否可交互和配置版本。
- `FR-NPC-04`：NPC 的坐标、碰撞、巡逻和交互范围由 Godot 确定性控制；LLM 不参与实时移动和物理逻辑。

### 5.6 日志与诊断

- `FR-LOG-01`：后端记录结构化请求日志、对话处理结果、模型耗时、记忆命中和关系规则结果。
- `FR-LOG-02`：每次请求有唯一 `request_id`，可串联 API、模型、数据库和错误记录。
- `FR-LOG-03`：日志不得记录 API 密钥、完整认证头或其他敏感配置。
- `FR-LOG-04`：运行日志和 SQLite 数据属于本地产物，不纳入 Git。

### 5.7 启动与发布

- `FR-RELEASE-01`：开发模式下可分别启动 FastAPI 和 Godot，并有明确的健康检查与启动说明。
- `FR-RELEASE-02`：首版交付 Windows 发布包。推荐目标是未安装 Godot 或 Python 的测试者也能启动 mock 模式体验核心流程。
- `FR-RELEASE-03`：真实模型配置缺失时自动使用 mock 模式，不因缺少密钥阻止启动。
- `FR-RELEASE-04`：发布包包含版本号、运行说明、配置示例和已知限制，不包含开发密钥、测试数据或个人对话记录。

## 6. 非功能需求

- `NFR-01 响应性`：移动、碰撞、开关 UI 和等待动画保持本地即时响应；网络请求异步处理。
- `NFR-02 稳定性`：后端不可达、模型超时、无效 JSON 和数据库重启后，游戏不崩溃、不冻结。
- `NFR-03 可维护性`：游戏表现、API、领域规则、模型适配和存储职责分离；NPC 内容数据化。
- `NFR-04 可测试性`：关系、记忆隔离、配置校验、API 和降级行为可在无真实 LLM 的环境下自动测试。
- `NFR-05 可迁移性`：LLM、长期记忆检索和存储通过边界接口隔离，为后续 Qdrant、Neo4j 或其他模型服务保留替换点，但首版不实现这些后端。
- `NFR-06 安全性`：所有状态变更由确定性服务执行；模型只接收必要上下文，不拥有高风险工具。
- `NFR-07 兼容性`：开发与验收以 Godot 4.7.1 和 Windows 为基准；Python 具体支持版本在设计阶段根据依赖兼容性确定。
- `NFR-08 视觉质量`：1280 x 720 下文字不重叠、不溢出，交互提示、对话框和等待/错误状态清晰可辨，原创占位资源保持统一像素尺度和视觉语言。

## 7. 首版不包含

- 多人在线、账号系统和 WebSocket 同步。
- 任务系统、背包、经济、战斗和复杂事件系统。
- 多场景小镇、昼夜循环和完整 NPC 日程。
- 独立情绪模型及复杂 NPC-NPC 社交关系。
- Qdrant、Neo4j、向量嵌入服务和 RL 训练。
- MCP、A2A、ANP 或对 Helix 源码的运行时依赖。
- 游戏内 NPC 管理后台与运行时热更新，除非用户在需求确认时将其加入首版。
- 将 AI 批量生成作为玩家实时对话的替代；AI 背景批量生成延后评估。

## 8. 验收标准

- `AC-01`：全新本地数据下启动发布包，能进入 1280 x 720 办公室场景并识别三名指定 NPC。
- `AC-02`：连续执行移动、碰撞、靠近提示、E 键交互、发送、收到回复和关闭对话，流程无阻断。
- `AC-03`：在 mock 模式分别与三名 NPC 对话，回复内容和表达风格可辨认，关系与历史分别保存。
- `AC-04`：告诉某 NPC 一个明确偏好，结束会话并重启后端后再次询问，该 NPC 能引用已保存事实；其他 NPC 不会错误引用。
- `AC-05`：通过配置修改一个 NPC 的显示名称和性格并重启，场景和对话均采用新配置，原 `npc_id` 的历史数据仍保留。
- `AC-06`：连续重复相同中性消息不能无限快速提高关系；正向与负向规则均有自动化测试证据。
- `AC-07`：断开后端或模拟模型超时，游戏仍可移动和关闭对话，UI 显示可理解的降级信息。
- `AC-08`：后端重启后，对话、关系和长期记忆恢复；SQLite 数据中不存在跨 NPC 或跨玩家串线。
- `AC-09`：后端自动化测试通过，Godot 无脚本解析错误，桌面运行与画面在至少 1280 x 720 下通过截图检查。
- `AC-10`：发布目录不含 `.env`、API 密钥、开发日志、SQLite 测试数据、Godot 导入缓存或 Python 缓存。

## 9. 需求确认前的待决事项

需求范围内的决策已经全部确认：

1. NPC 修改采用“本地配置文件 + 启动校验 + 重启生效”，首版不增加游戏内管理界面。
2. 发布物包含 Godot Windows 可执行文件、可独立启动的后端和一键启动入口，测试者无需安装 Godot 或 Python。

真实 LLM 的服务商、模型名、OpenAI API 兼容性、`base_url` 和环境变量名在开发模型适配前提供；不需要提供密钥内容，也不阻塞需求与设计确认。

## 10. 需求来源与修正原则

本需求来自用户提供的第十五章原文、15 张配图、CyberTown 初始空骨架和本轮确认的产品决策。

原文中的实现示例仅作为意图参考。以下内容不直接继承：常驻 NPC Agent 实例作为权威会话、LLM 直接决定关系分数、Qdrant/Neo4j 作为首版前置、将背景批量生成用于玩家即时对话、在多个 Godot 脚本内按 NPC 姓名写死分支。设计阶段必须用可测试、可持久化、可配置且不会阻塞游戏主循环的方案满足对应产品目标。
